# Account deletion request boundary

`users.index.requestDeletion` accepts the exact confirmation `DELETE` for the authenticated session; `deletionStatus` remains available to that owner. Both return `requested` only. The internal paginated `users.internal.deletionRequests` queue identifies outstanding requests and unverified work. Duplicate requests preserve their original time. No data or provider resource is deleted by requesting.

Agent admission, worker claim and next-message selection, worker compute-access checks, and agent credential issuance/authentication check the request marker. This does not interrupt a remote operation already in flight, revoke other credentials or sessions, block every provider or API route, or prove the remote sandbox stopped. Do not represent it as completed deletion or as a complete account lockdown.

Before completion can be implemented: fence and drain all user-initiated and already-running work, confirm remote sandbox and provider cleanup or document justified retention, handle production releases and manual Expo deletion, remove or retain user-owned app, preview, connection, file, agent, billing and telemetry records according to explicit policy, remove auth-provider identities and revoke all sessions using supported auth component APIs, then verify these outcomes and provide a durable completion receipt that does not rely on a revoked session. Keep failure and unknown outcomes resumable and operator-visible. Store submission remains blocked until that lifecycle and the public deletion path are delivered.

The internal operator queue includes the latest stop attempt, timestamp and lease deadline. An operator may invoke `agent.actions.compute.stopForDeletion` for a requested user; it takes an exclusive lease and uses the existing Boat refresh/normal-stop boundary. A missing sandbox record, exception, non-archived result or expired lease remains unknown. A later explicit attempt can retry. `archived_observed` records only the provider response at that moment; it does not prove that in-flight work was drained or cannot restart a sandbox. No automatic cleanup or completion follows. The `failed` state is available for a definitive operator-classified failure; this action conservatively records exceptions as unknown.

Pending accounts are denied the product REST authentication path, MCP tool dispatch and new MCP capability issuance, new connection-management requests, browser connection handoffs and connected Convex/Expo credential retrieval. These fences do not cover every native query or already-in-flight action, nor do they revoke pre-existing external credentials. Subsequent cleanup needs a narrowly scoped internal operator credential path, comprehensive authorization fences, in-flight drain, session revocation and provider-retention verification before a completion receipt can be issued.

An operator may explicitly invoke internal `users.mcpDeletion.runBatch` with the actual pending user ID and its matching `deletionRequestedAt`. Each call runs at most one MCP component erasure batch and atomically records cumulative counts and either `in_progress` or `attributed_complete` on that user's request. The internal request queue exposes that progress. Repeating a completed step returns the existing progress without adding counts; no work is automatically scheduled. The MCP component permanently retains a user-ID fence. The component's attributed completion covers only rows it can associate with that user: historical orphan token rows and unassociated pending authorization requests remain separately unresolved. It does not remove the user, revoke the login session, establish external provider cleanup, or change the public request status to completed.

Connection state creation/consumption, connection saves, PostHog refresh/selection and GitHub installation binding check the owner in the same transaction as the write. The PostHog refresh lease can still be cleared without replacing its token after a request. Product file upload checks the owner before writing storage and again in the registration mutation. If registration fails, the existing rollback attempts to remove the newly written object; rollback failure remains an explicit manual-cleanup error and neither denial nor an attempted rollback proves all remote objects are erased. An OAuth exchange or provider refresh already in flight can still finish remotely and may invalidate or create external credentials; those effects require reconciliation before deletion can complete. Auth component erasure is not yet integrated with a verified remote-work drain and remains a blocker.

An operator can call internal `users.authDeletion.runBatch` with a pending user ID and its exact request timestamp. In one transaction it fences core, password, username and email authentication before advancing bounded identity and linked core cleanup, retaining cumulative counts on the request. Repeat until `linked_auth_cleared`; retries after that state do not add counts. The fence revokes session access, so progress is operator-visible independently of the live session. Google identity cutoffs are retained as mappings are removed. Historical unattributed refresh tokens and email challenges remain unverified; provider identity digests and cutoffs are retained indefinitely, and re-registration for those identities is blocked. This stage may run while remote stop or MCP cleanup remains unknown; neither this stage nor MCP completion proves remote work drained or whole-account deletion. No user or provider resource is removed by this stage.

Legacy `.7` progress marked `linked_auth_cleared` is resumed until the username and attributed email fences and batches are complete; earlier counts are retained. The username and email components retain opaque user-ID tombstones indefinitely, and unattributed email challenges may remain. These retained records require a retention decision and do not establish whole-account deletion.

Internal `users.fileDeletion.runBatch` accepts only an exact pending user and request timestamp. It scans at most 20 owned Convex file records per call, removes an existing storage blob and its metadata in one mutation, and records deleted and already-missing counts. Shared storage IDs are retained and block the scan; R2 metadata is retained and reported as a blocker without contacting R2. The queue exposes the progress, including whether known Convex files have been cleared. Unregistered uploads, failed earlier rollback and other unattributed storage objects remain unverified, even when known Convex files are cleared. No provider resource, app, or user is removed by this stage.

Each authenticated deletion request atomically creates a durable request receipt with an opaque reference, the original request time and internal owner correlation. Existing pending owners can backfill it while authenticated. The user can download a plain-text receipt; the reference is not a credential and does not authorize public lookup. Internal support can resolve the reference or list receipt records independently of the user row. The retained owner correlation and reference need a retention policy. A receipt confirms only that a request was recorded; it does not confirm deletion or cleanup.
