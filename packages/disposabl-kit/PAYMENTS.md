# Payments setup

US iOS website checkout requires a verified monthly store offering, RevenueCat sync, an HTTPS `BILLING_RETURN_URL` ending in `/pricing`, and backend `MOBILE_WEB_CHECKOUT_ENABLED=true`. The app rechecks the StoreKit storefront and payment restrictions before opening a full browser. The browser confirms the account and the customer separately chooses the monthly purchase. Other storefronts and Android retain store purchasing. After checkout, return to the app and refresh; only the Autumn balance is credited. US iOS top-ups require a matching verified native consumable route and product; the app rechecks these before opening the browser.

The checkout attempt is recorded before the provider call. A lost or unfamiliar response stays unresolved and blocks another attempt for that customer and purchase type. The operator must check the corresponding Autumn and payment-provider records before invoking the internal `billing:resolveAttempt` with that customer, request ID, resolution outcome and provider evidence. A known checkout URL is retained against its request ID so a lost action response does not start another provider request. Provider URLs may be sensitive and should be protected as billing data.

App Review notes, 2026-11-08: the US StoreKit storefront sees equally styled monthly store and website options, the website option opens the external browser after a tap, and other storefronts retain IAP. Provide reviewers with configured test accounts and recheck current review rules before submission. This is source behavior, not evidence of a sandbox purchase, device verification, or App Review acceptance.

Payments is optional and includes authentication. Select `payments` in `disposabl.json`; the server checks this selection before reading credentials or calling Autumn. With it off, the pricing page blocks purchases and no billing credentials are needed. The authenticated Convex Auth user ID is the Autumn customer ID. Never use a client-supplied customer ID or price.

Before first setup, the **Autumn organization's default currency must match `pricing.currency`** in `payments/config.ts`, USD in the starter. Base price amounts use that organization currency; the create-plan request does not select a currency. Setup neither changes nor verifies the organization currency. Autumn `accounts.get` describes a customer group, not the organization, and cannot verify this prerequisite. Check the organization settings and both prices in Autumn before accepting purchases.

Configure `AUTUMN_SECRET_KEY` and `BILLING_RETURN_URL` on this app's Convex deployment. The return URL is needed for checkout, not catalog setup; it must be the absolute HTTPS URL of the app's `/pricing` page, without query or fragment. HTTP localhost is allowed for development. Use sandbox credentials for development and preview deployments and configure live credentials separately when ready to launch. Never store the secret in the frontend or `disposabl.json`.

## Catalog initialization

`payments/config.ts` is the editable source for plan IDs, prices, credits and currency. The default catalog has a consumable `credits` feature, a $5 monthly plan with 750 included credits resetting each month, and a $5 prepaid top-up with `billing_units: 500` and `interval: "one_off"`. The monthly multiplier changes the monthly allowance without changing top-ups. Top-ups have no reset or expiry configuration. Web checkout sends exactly that credit quantity. The web pricing page, mobile allowance text and optional Autumn configuration example use the same source.

The internal Convex action `billing:setup` takes `{}` and returns `{ enabled, created, preserved }`. It is re-exported by both the app backend and starter backend. With payments disabled, it returns before reading credentials or calling Autumn. When enabled without `AUTUMN_SECRET_KEY`, it fails with a setup message identifying the missing deployment credential. Customer checkout never initializes the catalog.

Setup uses the existing REST helper with API version `2.6.0`. It reads `features.list` and `plans.list` with `include_archived` and `all_versions`, validates both responses, then creates only missing configured IDs through `features.create` and `plans.create`. There are at most two reads and three creates per invocation. It never updates, deletes, archives or reactivates entries. Existing custom prices, credit definitions, archived plans and unrelated entries remain untouched. A preserved entry means its ID already exists, not that its pricing or usability matches the app. Review existing entries manually.

Any read error, including unauthorized or 404, stops setup without writes. A failed or uncertain create stops the invocation without an automatic retry. Rerun setup after checking the provider: the next run reads provider state and resumes from entries already created. Concurrent runs may collide and one may fail; rerunning preserves the winning entries. There is no cross-provider transaction, rollback or automatic reconciliation.

`bun run dev` starts the backend with `convex dev --run billing:setup`. The installed Convex CLI runs it after the first successful push in each dev process, against that same selected deployment. CI runs setup after `convex deploy` succeeds and before the web upload, using the same preview name or an explicit production target and the existing deploy key. Setup failure prevents that upload but does not undo the backend deploy. No new deployment selection or credentials are introduced.

For a manual retry, run from `packages/backend` with an explicit target: `bun x --no-install convex run --preview-name <channel> billing:setup '{}'` for the existing preview, or `bun x --no-install convex run --prod billing:setup '{}'` for production. For development, restart the existing dev process. Verify the target and its Autumn key first.

After editing prices, credits or currency for existing IDs, apply matching changes in Autumn and the native stores before deploying the app. Editing the local file does not update existing provider entries. `payments/autumn.config.example` is an optional manual reference, not an initialization step. If used, copy it and `config.ts` into a separate project with `atmn@2.0.218`, renaming it `autumn.config.ts`. Never automate `atmn push`: its complete catalog lists can delete unlisted plans and features.

Autumn documents one-off prepaid credits as nonexpiring; subscription credits reset each cycle. Provider transactions, repeated top-ups, renewals, cancellation and refunds still need sandbox verification. Do not promise subscription credits survive cancellation. The provider balance is authoritative; a redirect alone does not grant credits. This foundation does not implement usage charging.

The app calls Autumn API 2.6.0 `customers.get_or_create`, `billing.attach`, and `billing.open_customer_portal` server-side. Checkout uses server-owned plan IDs and the top-up quantity from `payments/config.ts`. Return to pricing may precede provider synchronization; use Refresh to read Autumn again. Setup and test Stripe checkout and portal in Autumn before enabling live use.

## Native subscriptions and synchronization

Generated apps include RevenueCat and the native billing example only when payments is selected. Reconfiguring payments adds or removes that SDK and its unchanged example files; unrelated dependencies are preserved. Customized billing files must be reconciled before disabling payments. Run installation after reconfiguration and build a new native binary when the SDK selection changes.

The account screen presents a RevenueCat paywall for the configured monthly subscription and supports restore. Its current offering must contain exactly that one monthly product; mixed or unverified products are unavailable. Use Autumn's managed RevenueCat integration as the sole sync path, with the same authenticated user ID as RevenueCat `appUserID` and Autumn `customer_id`. Request beta access, connect a RevenueCat project and V2 read-only key in Autumn, map store-level subscription products to `credits_monthly`, and configure separate test and live webhooks using Autumn's provided URL and authorization. Block duplicate web/native subscriptions based on the provider customer state. Mobile purchases use RevenueCat, never Autumn attach. Await Autumn webhook synchronization before treating the Autumn balance as available.

Set public build-time variables `EXPO_PUBLIC_REVENUECAT_IOS_API_KEY` and `EXPO_PUBLIC_REVENUECAT_ANDROID_API_KEY`, plus `EXPO_PUBLIC_REVENUECAT_IOS_MONTHLY_PRODUCT` and `EXPO_PUBLIC_REVENUECAT_ANDROID_MONTHLY_PRODUCT` to the exact store product identifiers. Configure each monthly product to match `pricing.monthly.price` in `payments/config.ts`, with no unverified offers, and map it to the Autumn monthly plan whose included credits come from `creditQuantity("monthly")`. The defaults are $5 and 750 credits per cycle. The app displays the store's localized price. Build a new native binary after adding the SDK; Expo Go is insufficient. Android uses `singleTop` when payments is selected so external bank verification can return to the purchase.

Only set backend `REVENUECAT_SYNC_ENABLED=true` after configuring and verifying the matching Autumn environment's managed integration. Without it, the app still reads shared credits but does not offer native purchases. Payments disabled means no billing component or SDK initialization. The SDK uses custom user IDs only and serializes account switching with purchase operations. Sign-out clears UI ownership without creating a RevenueCat anonymous ID. Configure RevenueCat restore behavior deliberately so a restore does not transfer another account's purchases unexpectedly.

Web checkout and native purchasing reject an existing or scheduled monthly plan, and native purchasing also checks RevenueCat's active subscriptions. Unknown provider state blocks a new subscription. Web monthly checkout reuses its single outstanding URL across tabs, devices and request IDs. Creating a URL does not release that guard. A pending monthly attempt also blocks the native subscription preflight, including when its provider outcome is unknown. After an operator resolves an attempt, the browser may discard that request ID and start a new checkout only on a new explicit purchase action. Unknown outcomes retain the same ID. An internal operator must verify the checkout completed, expired or was cancelled and record evidence through `billing:resolveAttempt` before allowing a replacement. This deliberately remains manual until provider checkout lifecycle reconciliation is verified. An unpaid but still payable link is not safe to release. These checks do not constitute a distributed transaction across concurrent web and store checkouts. Credits always come from Autumn; a store receipt is shown as awaiting synchronization, never added locally.

Native consumable top-ups use a separately fetched store product and the opt-in custom RevenueCat inbox; this is not provider or release proof. The native button remains disabled until the backend route and the public app and product IDs match and the operator explicitly verifies the integration. Its ownership must be exclusive: keep this top-up product out of Autumn's managed RevenueCat mapping, while managed subscriptions remain separate. Never enable custom grants for a product already granted by a managed integration. The inbox accepts an explicit allowlist of store apps and products within one RevenueCat project and environment.

With payments selected, custom processing is disabled unless `REVENUECAT_CONSUMABLE_OWNER=custom`, `REVENUECAT_WEBHOOK_AUTH`, `REVENUECAT_PROJECT_ID`, `REVENUECAT_ENVIRONMENT` (`SANDBOX` or `PRODUCTION`), `REVENUECAT_ROUTES`, and `AUTUMN_SECRET_KEY` are present. `REVENUECAT_ROUTES` is a JSON array such as `[{"app":"apple-app-id","store":"APP_STORE","product":"apple-topup"},{"app":"google-app-id","store":"PLAY_STORE","product":"google-topup"}]`. Each app ID must be unique. Invalid or ambiguous configuration disables the inbox. Configure a distinct authorization for each project and environment, sent as the complete Authorization header to `/revenuecat/webhook`. RevenueCat payloads do not normally include a project ID: the project association depends on that credential; authenticated app ID, store, environment and product select the allowlisted route. Transfer events without an environment are rejected for review. Use separate test and live deployments and secrets. Payments-off never processes a webhook or makes an Autumn request.

After completing the verification below, an operator may explicitly set `REVENUECAT_CONSUMABLE_INTEGRATION_VERIFIED=true` on the matching backend. Set `EXPO_PUBLIC_REVENUECAT_IOS_APP_ID`, `EXPO_PUBLIC_REVENUECAT_ANDROID_APP_ID`, `EXPO_PUBLIC_REVENUECAT_IOS_TOPUP_PRODUCT`, and `EXPO_PUBLIC_REVENUECAT_ANDROID_TOPUP_PRODUCT` to the exact route values for each build. The SDK fetches the localized store price and verifies the product identifier and non-subscription category. On iOS it requires StoreKit 2 to identify the product as consumable; StoreKit 1 cannot prove this. On Android the SDK may report an unknown specific product type, so the operator must independently verify its consumable configuration. Do not enable based on category alone. The monthly RevenueCat offering remains separate and contains only the monthly product.

The authenticated webhook checks app, environment, store, product, transaction and a known local user, then durably records delivery and transaction ownership. A stable balance ID excludes the customer, so an account switch cannot create a second grant. A scheduled worker atomically changes `queued` to `grant_unknown` before calling Autumn 2.6 `balances.create` with the configured top-up credit quantity. Only an explicit `{success:true}` response records a grant. A timeout, malformed response, provider error, or worker crash leaves `grant_unknown`: duplicate deliveries and action retries cannot issue another create. A separate paid transaction can proceed independently. The HTTP 202 response means accepted for processing, never credited.

A cancellation before dispatch creates a local tombstone; a later purchase cannot grant. Cancellation during a write is held until the result is known. After a grant, cancellation enters `refund_review` because the webhook alone does not prove the refund is full. An operator must establish the scope and spent-credit policy from provider records before calling private `revenuecat:confirmFullRefund` with a nonsecret evidence reference. It targets only that balance ID via `balances.update` with `remaining: 0`. An uncertain update is held as `refund_unknown`. Transfers and refund reversals require review; transfer notifications are stored separately and place affected customers on hold across both apps in the same project and environment. A transfer arriving after dispatch cannot cancel an in-flight provider request. There is no automatic hold release until transfer reconciliation is defined, and incomplete event identities are rejected. No automatic restore, replay of an uncertain operation, or missed-webhook reconciliation is implied.

Operators can inspect private `revenuecat:inspect` by state and `revenuecat:inspectTransfers` and `revenuecat:inspectConflicts`. `revenuecat:confirmUnknown` records a provider-confirmed grant or refund with a nonsecret evidence reference, without issuing another write. An aggregate customer balance alone is not proof of an individual operation. There is no automatic reissue of a failed or uncertain dispatch. A queued operation whose worker never started or found configuration missing needs an operator-run `revenuecat:dispatch` after confirming the same deployment and exact route configuration; unknown states cannot be claimed by that action.

Autumn documents a caller-supplied `balance_id`, not its atomic uniqueness and retry semantics. This code does not claim exactly-once behavior across providers. Before enabling or offering the consumable, verify stable ID behavior and balance targeting, event ownership, concurrent delivery, response loss, crashes, refunds and partial refunds in isolated Apple and Google sandboxes; establish a documented provider reconciliation contract and a missed-webhook process. A successful local test or a callback does not prove a purchase or provider write. Native product IDs, pricing, RevenueCat offerings and both stores still need verification; do not set the verification flag until those checks pass. A store purchase remains pending until the authoritative Autumn balance updates; the app never grants credits locally.

## Platform connection and starter packaging

Autumn's Platform API is private preview; its documented OAuth connects Stripe to a managed Autumn organization, not an existing Autumn account to Disposabl. Disposabl Connections accepts an encrypted sandbox key and an optional live key. It verifies each through the read-only `plans.list` endpoint. Payments selection requires this connection; other apps remain unblocked. Generator setup installs the sandbox key only on the named development backend, and the live key only on production when supplied. The platform billing key is never copied. Setup initializes `BILLING_RETURN_URL` only when absent, using that deployment's `/pricing` page; change it to your verified custom web origin if needed. Provisioning only installs credentials and the return URL. The deployed app initializes missing catalog entries from its own config through `billing:setup`. Verify both plans in each Autumn environment. Disconnecting or omitting a live key does not revoke credentials previously installed on an app; rotate those in Autumn and update each app explicitly.

The parent `reset.ts` replaces backend functions from `starter/backend`; both backends re-export the billing functions, including internal setup. The generated package retains the kit, editable payment config and backend dev hook. Both Convex configs declare the optional billing variables. Regenerate API types after backend functions change. Do not copy any parent credentials.

Catalog contracts were checked against the official API 2.6.0 docs and `autumn-js` 1.5.64 schemas; no SDK dependency is added. The get endpoints do not specify missing-resource error codes, so initialization uses complete list responses instead.
